# Как устроен проект — простое объяснение

## Идея

Цель проекта — проверить, помогают ли данные о поведении клиента по платежам лучше оценивать риск будущего дефолта, чем одни только базовые характеристики клиента.

## Шаг 1. Подготовка исходных данных

`src/prepare_data.py` читает UCI-датасет. В нём одна строка на клиента, а история платежей за шесть месяцев хранится в отдельных колонках.

Код превращает эту историю в более удобную таблицу `payment_history`: одна строка = один клиент в один месяц.

Затем создаются три таблицы SQLite:
- `clients` — базовые характеристики клиента;
- `outcomes` — произошёл ли дефолт в следующем месяце;
- `payment_history` — месячная история платежей.

## Шаг 2. Создание признаков в SQL

`sql/01_feature_mart.sql` собирает итоговую аналитическую таблицу `feature_mart`.

Главная идея — из шести месяцев истории получить компактные признаки поведения клиента. Например:
- какова последняя просрочка;
- как часто клиент раньше задерживал платежи;
- насколько большой была максимальная просрочка;
- растёт или уменьшается просрочка;
- какую долю кредитного лимита клиент использует;
- бывают ли месяцы без платежей.

После этого на каждого клиента остаётся одна строка, готовая для модели.

## Шаг 3. Деление данных

В `src/analyze.py` выборка делится примерно на:
- 60% train;
- 20% validation;
- 20% test.

Train используется для обучения. Validation — для выбора порога/проверки решений до финального теста. Test — для итоговой независимой оценки качества.

## Шаг 4. Модели

Сравниваются три варианта.

### Profile

Обычная логистическая регрессия только на базовых характеристиках:
- кредитный лимит;
- возраст;
- образование;
- семейное положение.

Это baseline: что мы можем предсказать, почти не используя историю поведения.

### Full

Та же логистическая регрессия, но к базовым характеристикам добавляются поведенческие признаки из истории платежей.

Именно эта модель используется для итогового Client Behavioral Risk Score.

### Boosting

`HistGradientBoostingClassifier` — более гибкая ML-модель, которая может находить нелинейные зависимости и взаимодействия между признаками.

Она нужна для сравнения: насколько более сложный алгоритм улучшает прогноз относительно обычной логистической регрессии.

## Шаг 5. Метрики

Для моделей рассчитываются:
- **ROC-AUC** — насколько хорошо модель ставит более рискованных клиентов выше менее рискованных;
- **Brier Score** — насколько близки предсказанные вероятности к фактическим исходам;
- **Log Loss** — штрафует модель за особенно уверенные неправильные вероятности;
- **Precision** — какая доля отмеченных моделью рискованных клиентов действительно дефолтная;
- **Recall** — какую долю всех дефолтов модель смогла найти.

## Шаг 6. Risk Score

Для каждого клиента Full-модель возвращает вероятность дефолта `pd` от 0 до 1.

Она переводится в более наглядную шкалу:

```text
risk_score = pd × 100
```

Например, `pd = 0.27` превращается в `risk_score = 27`.

Это не отдельная новая модель — просто вероятность дефолта в шкале 0-100.

## Шаг 7. Risk bands

Клиенты делятся на пять групп A-E по квантилям score на train-выборке.

Это позволяет смотреть на риск не только как на индивидуальное число, но и сравнивать группы клиентов.

## Шаг 8. Ограниченная ручная проверка

Проект моделирует бизнес-ситуацию, когда невозможно вручную проверить каждого клиента.

Test-клиенты сортируются по вероятности дефолта. Затем проверяется, сколько дефолтов можно поймать, если команда способна проверить только:
- 5%;
- 10%;
- 20%
самых рискованных клиентов.

Для этого рассчитываются Precision, Recall/Capture и Lift.

## Шаг 9. statsmodels

Помимо sklearn используется `statsmodels.Logit` с той же спецификацией логистической регрессии.

Он нужен не для второй отдельной модели, а для статистического анализа коэффициентов: standard error, p-value, confidence interval и odds ratio.

## Шаг 10. Проверки

`src/verify.py` автоматически проверяет, что:
- клиентов 30 000;
- у каждого клиента шесть строк истории;
- score находится от 0 до 100;
- нет пропусков;
- test содержит 6 000 клиентов;
- одинаковые исходные наблюдения не попали в разные splits;
- score можно точно восстановить из сохранённых коэффициентов модели.

Это простые sanity checks, которые помогают убедиться, что pipeline не сломался.
